## 1. Что делаем (одним абзацем)

Инструмент для сотрудника **подразделения по профилактике коррупционных правонарушений**. «Посейдон» смотрит на
имущество (это следствие), а мы смотрим на **решения** служащих: кому отдан контракт, как прошла процедура,
соблюдены ли полномочия. Система находит решения с **признаками риска**, объясняет, какое правило сработало,
и показывает документ-основание. **Решение принимает человек.** Система никогда не выносит вердикт
«служащий коррумпирован» и не строит рейтинг «коррупционности» людей.

Опора признаков:
- методика Минтруда (письмо от 25.12.2014 № 18-0/10/В-8980, п. 13 — признаки коррупционного поведения);
- индексы риска по госзакупкам (Fazekas et al., «красные флаги»: единственная заявка, доля победителя и т. д.).

## 2. Требования брифа, которые проверят (не нарушать)

| Требование | Как обеспечиваем |
|---|---|
| Ключевой сценарий работает целиком | Демо: данные → сигналы → карточка → граф → документ |
| Одинаковый вход → одинаковый результат | seed, сортировка, без случайности и облачных LLM в конвейере |
| Пользователь видит причину сигнала | У каждого сигнала: правило, значения, порог, группа сравнения, ссылка на фрагмент документа |
| Решение о человеке принимает человек | В UI статус сигнала ставит пользователь: «принят в работу / отклонён» + комментарий |
| Синтетика не выдаётся за реальные данные | Пометка источника у каждой записи (`source = synthetic/real`) |
| Инструкция запуска | `docker compose up` + README с версиями |

## 3. Объём MVP (что входит и что нет)

**Входит:**
1. Генератор синтетики: ведомство, подразделения, служащие, группы, организации, родственники, закупки, документы.
2. **Блок 1 — граф групп**: иерархия, проектные группы, закупочные комиссии, связи с организациями-контрагентами.
3. **Блок 2 — индикаторы** И1, И2, И3, И4, И7 (раздел 7) с группами сравнения.
4. **Модуль распознавания (Гасан)**: протоколы закупочных комиссий и приказы о создании рабочих групп → JSON.
5. Оценка качества: recall/precision по внедрённым схемам; F1 распознавания.
6. UI: список сигналов, карточка сигнала, граф связей, просмотр документа с подсветкой.

**Не входит (в паспорт как «следующий шаг»):** И5 (дробление), И6 (сроки рассмотрения), И8 (НИР против научных
статей), сравнение со стратегиями, данные ФНС, ML-взвешивание индикаторов.

## 5. Схема данных

```sql
-- Оргструктура
units(id, name, parent_id, level)                       -- ведомство → департамент → отдел
positions(id, unit_id, title, function_code)            -- function_code: PROC, LIC, CONTROL, HR, OTHER
position_authorities(position_id, action)               -- что должность вправе делать: SIGN_CONTRACT, APPROVE_PROC, ...
employees(id, full_name, position_id, hired_at, source)

-- Люди и организации вне госслужбы
persons(id, full_name, source)                          -- родственники, руководители и учредители фирм
organizations(id, name, inn, ogrn, okved, registered_at, source)
org_roles(org_id, person_id, role)                      -- DIRECTOR, FOUNDER

-- Блок 1: связи и группы
relations(id, a_type, a_id, b_type, b_id, rel_type, source, evidence_doc_id)
    -- rel_type: RELATIVE, EX_EMPLOYER, SAME_PROJECT, SAME_COMMISSION
groups(id, kind, name, created_by_doc_id)               -- kind: PROJECT, COMMISSION, WORKGROUP
group_members(group_id, member_type, member_id, role)

-- Блок 2: деятельность
procurements(id, unit_id, okpd2, method, nmck, published_at, deadline_at, commission_group_id, responsible_employee_id)
    -- method: AUCTION, TENDER, QUOTATION, SINGLE_SUPPLIER
bids(id, procurement_id, org_id, price)
contracts(id, procurement_id, supplier_org_id, price, signed_at, signer_employee_id)
amendments(id, contract_id, signed_at, price_delta, reason)

-- Документы
documents(id, doc_type, path, source)                   -- PROTOCOL, ORDER, CONTRACT
doc_fragments(id, document_id, page, char_start, char_end, text)

-- Результат
signals(id, indicator, object_type, object_id, employee_id, value, threshold, peer_group, explanation,
        evidence_fragment_ids, status, reviewer_comment)  -- status: NEW, IN_WORK, REJECTED

-- Ground truth (только для оценки, в UI не показывать)
injected_schemes(id, scheme, object_type, object_id, employee_id)
```

## 6. Генератор синтетики

Параметры в `config/settings.yaml`, по умолчанию:

| Параметр | Значение |
|---|---|
| seed | 42 |
| подразделения | 1 ведомство → 5 департаментов → 20 отделов |
| служащие | 150, из них ~30 с функцией PROC |
| организации | 300 |
| родственники | у ~10% служащих 1–2 родственника, часть из них руководит фирмами |
| закупки | ~2000 за 2 года (2024–2025) |
| допсоглашения | у ~15% контрактов |

**Фон (честное поведение)** должен содержать правдоподобный шум, иначе индикаторы будут тривиальны:
единственные заявки на узких рынках, крупные поставщики с большой долей, законные допсоглашения.

**Внедряемые схемы (ground truth):**

| Код | Схема | Как внедрить | Какие индикаторы должны найти |
|---|---|---|---|
| S1 | Аффилированный поставщик | Родственник служащего — директор фирмы; фирма выигрывает закупки, где служащий ответственный или в комиссии | И2, И1 |
| S2 | Концентрация | У 3 служащих одна фирма получает >60% стоимости контрактов | И1 |
| S3 | Ограничение конкуренции | Короткий срок подачи + единственная заявка у одного ответственного систематически | И3 |
| S4 | Раздувание цены | Снижение на торгах ~0%, затем допсоглашения с ростом цены ≥10% | И4 |
| S5 | Сверх полномочий | Контракты подписаны должностью без SIGN_CONTRACT в `position_authorities` | И7 |

Генератор также создаёт **документы** (PDF/DOCX): протоколы комиссий (состав, участники, цены, победитель) и
приказы о создании рабочих групп (состав, роли). Это даёт Гасану размеченный корпус бесплатно. Добавить 2–3
шаблона формулировок на тип документа и мелкий шум (переносы строк, разный порядок полей), чтобы парсер не был
подогнан под один шаблон.

## 7. Индикаторы

Общее:
- **Группа сравнения** = (`function_code` или первые 2 знака ОКПД2, год). Пороги — перцентили по группе, а не
  абсолютные числа (кроме законодательных).
- **Минимальный объём**: индикатор на уровне служащего считается, если у него ≥ 5 решений в группе.
- Каждый `Signal` хранит: значение, порог, группу сравнения, человекочитаемое объяснение, id фрагментов документов.
- Итог по решению = список сработавших индикаторов с весами из конфига. **Никакого единого «индекса человека».**
  В UI по служащему: «N решений с сигналами из M».

| Код | Уровень | Формула | Сигнал, если | Объяснение (шаблон) |
|---|---|---|---|---|
| И1 Концентрация | служащий | `share_top = max_s Σprice(e,s) / Σprice(e)` по контрактам, где e ответственный | `share_top > P90(group)` и ≥ 5 контрактов | «62% стоимости контрактов — у ООО «X»; у коллег по функции P90 = 35%» |
| И2 Аффилированность | контракт | В графе есть путь длины ≤ 2 от ответственного/подписанта/члена комиссии до директора или учредителя поставщика по рёбрам RELATIVE, EX_EMPLOYER, SAME_PROJECT | путь найден | «Директор поставщика — родственник члена комиссии (приказ №…, стр. 1)» + сам путь |
| И3 Конкуренция | служащий + закупка | Доля закупок с 1 заявкой в конкурентных процедурах; срок подачи заявок | доля > P90(group) **или** срок < P10(group) | «7 из 9 конкурентных закупок — с единственной заявкой (P90 у коллег = 3 из 9)» |
| И4 Цена | контракт | `drop = 1 − price/nmck`; `growth = Σprice_delta / price` | (`drop < 0.5%` при ≥ 2 заявках) **или** `growth ≥ 10%` **или** ≥ 2 допсоглашения с ростом цены | «Снижение на торгах 0,2%, затем +11% допсоглашениями» |
| И7 Полномочия | контракт | Действие подписанта ∉ `position_authorities` | нарушение | «Подписал заместитель начальника отдела; право подписи по регламенту только у директора департамента» |

Пороги (0.5%, 10%, P10/P90, минимум 5) — в `settings.yaml`, чтобы их можно было обсуждать и менять.
Порог 10% роста цены связан с допустимым изменением цены контракта по ст. 95 44-ФЗ — **перепроверить по
актуальной редакции перед защитой**.

## 8. Модуль распознавания (контракт для Гасана)

**Вход:** путь к PDF/DOCX. **Выход:** JSON

```json
{
  "doc_id": "protocol_0153",
  "doc_type": "PROTOCOL",
  "entities": [
    {"type": "PERSON", "value": "Иванова Ивана Ивановича", "normalized": "Иванов Иван Иванович",
     "role": "COMMISSION_MEMBER", "page": 1, "span": [312, 335]},
    {"type": "ORG", "value": "ООО «Ромашка»", "normalized": "ООО РОМАШКА", "page": 1, "span": [601, 614]},
    {"type": "INN", "value": "7707083893", "valid_checksum": true, "page": 1, "span": [630, 640]},
    {"type": "MONEY", "value": "1 250 000,00 руб.", "normalized": 1250000.00, "page": 2, "span": [88, 105]}
  ],
  "relations": [
    {"type": "BID", "from": "ORG:ООО РОМАШКА", "to": "MONEY:1250000.00", "evidence_span": [601, 105]},
    {"type": "WINNER", "from": "ORG:ООО РОМАШКА", "to": "PROCUREMENT:0153", "evidence_span": [700, 760]}
  ]
}
```

Порядок работы:
1. `requisites.py`: регулярные выражения + контрольные суммы (ИНН 10/12, ОГРН 13/15, счёт по ключу с БИК). Это
   детерминированно и легко тестируется — начать с этого.
2. `ner.py`: Natasha для ФИО и организаций + нормализация ФИО в именительный падеж (нужна для склейки).
3. `protocol.py`, `order.py`: правила по структуре документа (разделы «Состав комиссии», «Участники», «Решение»).
4. LLM — не нужна для MVP. Если подключать, то только локальную, температура 0, кэш по хэшу документа.
5. Оценка: F1 по каждому типу сущностей на документах генератора + 10–20 вручную размеченных «живых» документов
   (реальные протоколы с zakupki.gov.ru, если удастся скачать вручную).

**Важно:** демо должно работать и без этого модуля (граф строится из БД). Модуль добавляет рёбра из документов
и ссылки на фрагменты в карточках сигналов.
