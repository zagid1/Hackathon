# Сигналы риска в деятельности служащих — прототип

Хакатон «Код прозрачности», направление 4. Полная спецификация — [PLAN.md](PLAN.md).

**Статус: Этапы 1–3 готовы.** Этап 1 — скелет, схема данных, генератор синтетики со схемами S1–S5 и
ground truth, документы (DOCX) с разметкой. Этап 2 — граф связей, индикаторы И1–И4, И7 (`make signals`),
оценка recall/precision (`make eval`), распознавание реквизитов и ФИО/организаций. Этап 3 — парсеры
протокола и приказа (`make extract`), рёбра из документов в графе, UI на Streamlit (`make app`):
список сигналов → карточка → граф связей → документ с подсветкой.

> Все данные синтетические: ведомство, люди и организации вымышлены, у каждой записи `source = 'synthetic'`.

## Запуск

Docker (Python 3.11, как на защите):

```bash
docker compose up --build
```

Сначала сервис `pipeline` выполняет `make data extract signals eval` (несколько минут: генерация DOCX
и распознавание ~1500 документов), затем `ui` открывает интерфейс на http://localhost:8501.
Тесты в контейнере:

```bash
docker compose run --rm pipeline make test
```

Локально (нужен Python 3.11+; на Windows без `make` — команды справа):

| make | без make |
|---|---|
| `make data` | `python -m src.generator.run` |
| `make extract` | `python -m src.extraction.pipeline` |
| `make signals` | `python -m src.indicators.run` |
| `make eval` | `python -m src.evaluation.signals_eval` |
| `make app` | `python -m streamlit run src/app/streamlit_app.py` |
| `make test` | `python -m pytest` |

Параметры генератора: `--seed N`, `--out DIR`, `--no-docs` (строки документов в БД есть, DOCX не пишутся;
~1 с вместо ~70 с). Результат: `data/synthetic/synthetic.db` и `data/synthetic/docs/*.docx` + `*.json`.

Версии: Python 3.11, зависимости с точными версиями — в [requirements.txt](requirements.txt).
`networkx` 3.7+ и `numpy` 2.5+ уже требуют Python 3.12 — поэтому закреплены 3.6.1 и 2.4.6.

## Воспроизводимость

`make data` печатает два хэша:

* `db_sha256` — побайтный хэш файла БД; одинаков при одном seed в одном окружении (в заголовок файла
  SQLite пишет свою версию, поэтому между ОС может отличаться);
* `content_sha256` — хэш содержимого всех таблиц; одинаков на любой машине. Для seed 42 он равен
  `d79a4110…3e84c` (проверено на Windows/Python 3.12 и Docker python:3.11-slim) и закреплён в
  `tests/test_determinism.py`.

`make signals` печатает `signals_sha256` — хэш вычисляемых колонок таблицы `signals` (без статуса и
комментария проверяющего). Для seed 42: `8bb8d7e5…54639`, одинаков в обоих окружениях, закреплён в
`tests/test_indicators.py`.

Как обеспечено: отдельный поток `random.Random(f"{seed}:{модуль}")` на каждый модуль; деньги — в целых
копейках; никаких `math.log/exp` над случайными числами; суммы float — только через `math.fsum`
(встроенный `sum()` в Python 3.12 считает иначе, чем в 3.11 — на этом уже спотыкались); DOCX
перепаковывается с фиксированным временем и метаданными. Внешних API и облачных LLM нет.

Честный шум в фоне: единственная заявка в ~26% конкурентных закупок, крупные поставщики с большой

### Внедрённые схемы

| Код | Что внедрено | Строки ground truth | Должен найти |
|---|---|---|---|
| S1 | Родственник ответственного (3 служащих) или члена комиссии (1) — директор/учредитель фирмы; фирма выигрывает ~половину «их» закупок на своём рынке | контракты | И2 (И1 — по служащему) |
| S2 | У 3 служащих «своя» фирма получает > 60% стоимости контрактов (74–86% при seed 42) | служащие | И1 |
| S3 | У 2 служащих ~60% конкурентных закупок — минимальный срок подачи + одна заявка | служащие + закупки | И3 |
| S4 | У 2 служащих ~35% торгов: ≥ 2 заявки, снижение < 0,4%, затем 2 допсоглашения с ростом ≥ 10% | контракты | И4 |
| S5 | 2 начальника/заместителя начальника отдела без права подписи подписывают ~12% контрактов своего отдела | контракты | И7 |

Тесты проверяют каждую схему по самой БД (например, доля у S2 > 0,6; у S5 и только у S5 подписант без
`SIGN_CONTRACT`), а также что фон не содержит прямого родства.

### Документы и разметка (для модуля распознавания)

Каждый DOCX сопровождается JSON-разметкой в формате раздела 8 PLAN.md (PERSON с нормализованным ФИО,
ORG, INN, OGRN, MONEY; связи BID, WINNER, MEMBER; поле `ref` указывает на строку БД). На тип документа —
3 шаблона: разные падежи ФИО (именительный, родительный, винительный, инициалы), список или таблица,
5 форматов сумм, полное/краткое наименование организации, неразрывные пробелы, переносы строк.

Координаты `page`/`span` считаются по канонической модели текста: страницы разделены явными разрывами,
блоки (абзацы и строки таблиц, ячейки через ` | `) соединены `\n`. Эту модель реализует
`src.generator.documents.read_docx_pages()` — её стоит переиспользовать в `src/extraction`.
Примеры: [data/samples](data/samples) (2 приказа, 3 протокола — по одному на шаблон).

## Индикаторы (Этап 2)

| Код | Уровень | Правило (пороги — `config/settings.yaml`) | Группа сравнения |
|---|---|---|---|
| И1 | служащий | доля top-поставщика в стоимости контрактов > P90 коллег, ≥ 5 контрактов | функция + год |
| И2 | контракт | путь ≤ 2 по RELATIVE / EX_EMPLOYER / SAME_PROJECT от ответственного, членов комиссии или подписанта до поставщика либо его директора/учредителя | — (правило) |
| И3 | служащий + закупка | доля единственных заявок > P90 коллег или средний запас срока подачи сверх минимума < P10; закупки служащего с сигналом: 1 заявка и запас ≤ P10 по (способ, год) | функция + год |
| И4 | контракт | снижение < 0,5% при ≥ 2 заявках, или рост цены допсоглашениями ≥ 10%, или ≥ 2 допсоглашения с ростом | абсолютный порог |
| И7 | контракт | у должности подписанта нет `SIGN_CONTRACT` в `position_authorities` | регламент |

Перцентили считаются по коллегам без самого служащего (leave-one-out), чтобы выброс не поднимал
собственный порог. У каждого сигнала: значение, порог, группа сравнения, объяснение и id фрагментов
документа-основания (протокол, приказ о комиссии/группе). При повторном `make signals` статус и
комментарий проверяющего сохраняются. Единого «индекса человека» нет: `decision_summary` даёт по
решению список индикаторов с весами, `employee_overview` — «N решений с сигналами из M».

### Метрики на синтетике (seed 42, `make eval`)

| Схема → индикатор | Recall | | Индикатор | Precision |
|---|---|---|---|---|
| S1 → И2 (контракты) | 60/60 | | И1 (служащие) | 4/4 |
| S1 → И1 (служащие) | 1/4 | | И2 | 60/89 = 0,67 |
| S2 → И1 | 3/3 | | И3 (служащие) | 2/7 = 0,29 |
| S3 → И3 (служащие / закупки) | 2/2 / 26/26 | | И3 (закупки) | 26/28 = 0,93 |
| S4 → И4 | 42/42 | | И4 | 42/75 = 0,56 |
| S5 → И7 | 29/29 | | И7 | 29/29 |

precision@50 = 0,66; «чистых» контрактов с сигналом — 61 из 1791 (3,4%).
Recall 1,0 — ожидаемо: схемы внедрены нами и индикаторы построены под них; это проверка работоспособности,
а не оценка на реальных данных. Ложные срабатывания — заложенный шум: И2 — пути через общие проектные
группы и бывших работодателей (особенно путь из двух проектных рёбер), И3 — служащие, ведущие узкие
рынки (группа «функция + год» не учитывает рынок), И4 — малое снижение цены без последующих допсоглашений.
Разбор и подбор порогов — Этап 4.

## Распознавание (Этап 2: реквизиты и NER)

* `src/extraction/requisites.py` — ИНН 10/12, ОГРН/ОГРНИП, БИК, расчётный и корреспондентский счёт по
  ключу с БИК; тип определяется ключевым словом слева, без него — по контрольной сумме.
* `src/extraction/ner.py` — полные ФИО в любом падеже (правило + нормализация pymorphy3 с учётом рода),
  инициалы (правило), организации с ОПФ (правило, нормализация «ООО РОМАШКА»), прочее — Natasha.
  На документах генератора: ФИО 434/434 (границы и нормализация), инициалы 211/211, организации 228/228.
  Это свои же шаблоны — на реальных протоколах качество будет ниже; F1 на «живых» документах — Этап 4.
* Natasha 1.6.0 зависит от `pymorphy2`, который не работает на Python ≥ 3.11; `ner.py` при импорте
  подменяет его совместимым форком `pymorphy3`.

## Распознавание документов и UI (Этап 3)

`make extract` (`src/extraction/pipeline.py`): DOCX → JSON по контракту раздела 8 в
`data/synthetic/extracted/`; тип документа — по заголовку; кэш по sha256 файла и версии парсеров;
~0,1 с на документ (≈3 мин на весь корпус). PDF пока не поддерживается — понятная ошибка; следующий шаг — pdfplumber.

* `protocol.py` — состав комиссии с ролями (ключевое слово слева/справа в строке), участники с ИНН/ОГРН и
  ценами (в т.ч. из таблицы), победитель и цена контракта, НМЦК; связи BID и WINNER.
* `order.py` — номер, дата, вид и название группы, участники с ролями, внешние участники и их
  организации (AFFILIATION), подписант.
* Подписи инициалами склеиваются с полными ФИО того же документа, только если кандидат один
  (две «Соболевы А. А.» в одной комиссии остаются инициалами — угадывать нельзя).

Качество на корпусе генератора (свои шаблоны — на реальных документах будет ниже): протоколы — суммы,
ИНН/ОГРН, организации, связи BID/WINNER 100%, ФИО 1240/1260 (остальное — неоднозначные инициалы);
приказы — номер/дата/название 26/26, роли 160/160, ФИО 134/160 (не восстановлен подписант с инициалами:
в документе нет его полного ФИО).

Граф (`src/graph/build.py`, `add_document_edges`): рёбра из документов — член группы (приказ),
представитель организации (приказ), член комиссии / заявка / победитель (протокол); у ребра
`source = "document"` и id документа. ФИО сопоставляются со служащими и лицами из БД (инициалы — только
при однозначном совпадении), организации — по нормализованному наименованию. Тест проверяет, что рёбра
из документов не противоречат БД.

UI (`src/app/`): фильтры по индикатору, статусу и ФИО; карточка — объяснение, значение, порог, группа
сравнения, «N решений с сигналами из M» по служащему, фрагменты-основания, решение проверяющего
(«Новый / Принят в работу / Отклонён» + комментарий, сохраняется в `signals` и переживает повторный
`make signals`); граф связей (pyvis, пунктир — связь из документа, красный — путь И2); документ с
подсветкой фрагментов и скачиванием DOCX. Ground truth (`injected_schemes`) в UI не используется.

## Отличия схемы от раздела 5 PLAN.md (на согласование)

* `source` есть у всех основных таблиц (units, groups, procurements, bids, contracts, amendments и др.),
  а не только у пяти — требование брифа «пометка источника у каждой записи»;
* в `documents` добавлены `object_type`, `object_id`, `doc_number`, `doc_date` — иначе протокол не
  связать с закупкой;
* добавлены действие `RESPONSIBLE_PROC` в полномочиях и таблица `dataset_meta` (seed, хэш конфига).
