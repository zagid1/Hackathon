# Сигналы риска в деятельности служащих

Прототип для хакатона «Код прозрачности» (РАНХиГС), направление 4. Инструмент для сотрудника
подразделения по профилактике коррупционных правонарушений: находит в **решениях** служащих
(кому отдан контракт, как прошла процедура, соблюдены ли полномочия) признаки риска, объясняет,
какое правило сработало, и показывает документ-основание.

**Решение принимает человек.** Система не выносит вердикт о служащем и не строит рейтинг
«коррупционности»: у сигнала есть статус «Новый / Принят в работу / Отклонён», его ставит проверяющий.

> Все данные **синтетические**: ведомство, люди, организации и документы вымышлены, у каждой записи
> `source = 'synthetic'`. Внешних API и облачных LLM нет — всё работает локально и офлайн.

## Запуск

Нужен Docker с Compose v2 (проверено: Docker 29.9.2, Compose v5.6.1; образ ~1,1 ГБ).

```bash
docker compose up --build
```

1. Сервис `pipeline` готовит данные — `make data extract signals eval`: генерация 2000 закупок и ~1500
   документов (DOCX), распознавание документов, расчёт сигналов, оценка качества. Около 5 минут при
   первом запуске.
2. Затем сервис `ui` открывает интерфейс: **http://localhost:8501**.

Повторный `docker compose up` использует уже созданные данные из `./data` (распознавание кэшируется).
Решения проверяющего сохраняются в `data/synthetic/synthetic.db`.

Тесты (99 шт.): `docker compose run --rm pipeline make test`.

### Без Docker

Python 3.11 или 3.12:

```bash
python -m venv .venv
.venv/bin/pip install -r requirements.txt        # Windows: .venv\Scripts\pip
make data extract signals eval                   # или по шагам, см. таблицу ниже
make app                                         # http://localhost:8501
```

| Шаг | make | без make (Windows) |
|---|---|---|
| Синтетические данные (seed 42) | `make data` | `python -m src.generator.run` |
| Распознавание документов | `make extract` | `python -m src.extraction.pipeline` |
| Сигналы риска | `make signals` | `python -m src.indicators.run` |
| Оценка сигналов | `make eval` | `python -m src.evaluation.signals_eval` |
| Оценка распознавания | `make eval-extract` | `python -m src.evaluation.extraction_eval` |
| Таблица метрик | `make metrics` | `python -m src.evaluation.report --full` |
| Интерфейс | `make app` | `python -m streamlit run src/app/streamlit_app.py` |
| Тесты | `make test` | `python -m pytest` |

## Что посмотреть в демо

Сквозной сценарий: **данные → сигналы → карточка → граф → документ**.

1. **Список сигналов** — фильтры по индикатору, статусу и ФИО служащего.
2. **Карточка** — какое правило сработало, значение, порог, группа сравнения, объяснение
   («62% стоимости контрактов — у ООО «X»; у коллег по функции P90 = 35%»), фрагменты документов,
   «N решений с сигналами из M» по служащему; кнопки решения проверяющего.
3. **Граф связей** — путь от участника закупки к поставщику (например, «член комиссии — родственник
   директора поставщика»); пунктир — связь, найденная в документе.
4. **Документ** — протокол или приказ с подсвеченным фрагментом-основанием; можно скачать DOCX.

Хороший пример для показа — любой сигнал «И2 Аффилированность» с объяснением «родственник».

## Индикаторы

| Код | Что ищет | Опора |
|---|---|---|
| И1 Концентрация | у служащего одна фирма получает долю стоимости контрактов выше P90 коллег | индексы риска госзакупок (Fazekas et al.) |
| И2 Аффилированность | связь участника закупки с поставщиком или его руководителем (родство, бывший работодатель, общий проект) | методика Минтруда, п. 13 |
| И3 Конкуренция | систематически единственные заявки сверх нормы рынка, короткие сроки подачи | «красные флаги» госзакупок |
| И4 Цена | снижение на торгах < 0,5% при нескольких заявках, рост цены допсоглашениями ≥ 10% | ст. 95 44-ФЗ, «красные флаги» |
| И7 Полномочия | контракт подписан должностью без права подписи по регламенту | регламент полномочий |

Пороги — в [config/settings.yaml](config/settings.yaml). Группа сравнения — коллеги той же функции за тот
же год; перцентили считаются без самого служащего.

## Качество (на синтетике)

Полная таблица — [reports/metrics.md](reports/metrics.md) (`make metrics`). Правила подбирались на seed 42,
проверены на отложенных seed 1–5.

* Recall по пяти внедрённым схемам — 1,0 на всех seed; precision@50 — 0,84 (отложенные: 0,72–0,94).
* Доля «чистых» контрактов хотя бы с одним сигналом — 2,5%.
* Распознавание на корпусе генератора: F1 = 1,0 (ФИО — 0,987). На вручную написанных документах в стиле
  реальных протоколов ЕИС (слепой набор): ФИО 0,97, организации 0,89.

Это проверка работоспособности, а не оценка на реальных данных: схемы внедрены нами.

## Воспроизводимость

Одинаковый seed → одинаковые данные и сигналы на любой машине: `make data` печатает `content_sha256`,
`make signals` — `signals_sha256`; для seed 42 они закреплены в тестах и совпадают на Windows/Python 3.12
и в Docker (Python 3.11). Случайность — только из генератора с фиксированным seed; в конвейере её нет.

## Ограничения

* Данные синтетические; на реальных протоколах ЕИС распознавание не проверено (выгрузка требует
  сертификата) — это главный риск.
* Документы — только DOCX; PDF пока не читается (следующий шаг — pdfplumber).
* Нормы 44-ФЗ в генераторе упрощены; порог 10% роста цены (ст. 95) нужно сверить с актуальной редакцией.
* Не реализованы И5 (дробление), И6 (сроки рассмотрения), И8 (НИР) — следующий шаг.
